# i125pro 博客写作 / 改稿指南（给 AI agent）

这份文档给任何要为本博客写新文章或改旧文章的 agent 用。照着做，不要自由发挥。

## 读者是谁

一个自己折腾 VPS、代理、命令行工具的普通爱好者，**不是网络或系统专家**。他应该能从头读到尾不用去搜任何词。

## 博主最讨厌的问题

- 没有重点：读完不知道这篇到底要说什么。
- 跳跃：前一段还在讲 A，下一段突然讲 C，B 没交代。
- 门槛高：术语直接丢出来，不解释。
- 啰嗦、像 AI 写的：反复总结、自我辩护、元叙述、满屏加粗。

## 文章结构（默认骨架）

1. **开头 2–4 句**：发生了什么 / 要解决什么问题 + 一句核心结论。不写"先把结论放这儿""本文将介绍""下面按……排列"这类导航废话。
2. **为什么**：用一句白话或一个生活类比讲清原理。
3. **怎么做**：编号步骤，按读者实际操作的顺序。每一步写清楚在哪台机器上执行、预期看到什么。
4. **我踩的坑**：短，每条一两句，说现象和原因。
5. **速查**（可选）：只放命令，不重复解释。

每个二级标题只回答一个问题，标题直接说这一节给读者什么（例如"30 秒自检：你是不是同一个问题"），不要用"背景""分析"这种空标题。

## 术语

- 第一次出现必须用一句大白话解释，最好带类比。例：SNI 像写在信封外面的收件人地址，邮局不拆信也能看到。
- 只解释一次，后面直接用。
- 能不用的术语就不用。

## 删什么

- 重复的结论、"一句话总结"、"诚实的结论是"、"这一节比结论更值钱"。
- 自我辩护和过度谨慎的旁白。
- "给 AI / 自动化脚本的速查"之类的区块。
- 把正文换个说法再列一遍的表格。
- 过多加粗：一段最多一处，最好没有。
- emoji。

## 不要写成 AI 腔

不要出现：连续的"不是 X，而是 Y"、"一句话："、"值得一提的是"、"那么问题来了"、破折号串、一行一个的加粗金句、自问自答式小标题。

用一个冷静的工程师跟朋友讲事情的口吻，第一人称可以。

## 事实与代码

- 命令、数字、报错原文、日期、链接、文件路径、占位域名/IP **一字不改**。
- 不编造新的数字、结论或引用。原文说不清的地方，宁可写简单也不要猜。
- 改稿时发现原文有事实问题（数字对不上、说法过头），不要擅自补新论断；改成更保守的说法，并在交付说明里列出来让博主确认。
- 代码块、mermaid 图保留；mermaid 只是重复正文时可以删。

## Front matter 与文件

- 文章在 `_posts/`，中文版文件名带 `-zh`，英文版不带（早期文章例外，照现有命名）。
- 保留 `permalink`、`lang`、`keywords`、`mermaid` 不变；`title` 可以收紧；`description` 改成一两句平实的话，和正文一致。
- 站内互链的 URL 不能断。
- 英文版是**新中文版的翻译**，结构和内容一致，用自然英文，不是逐字硬译。
- 中文用自然的大陆简体中文，不要翻译腔。

## 篇幅

目标是原文的 50–70%，但**不能为了字数删掉读者复现需要的命令或数据**。代码多的文章压不下去是正常的。

## 交付

- 在新分支上改，不要直接推 `main`。
- 交付时说明：每个文件新旧字数、改了哪些结构、哪些事实你不确定以及怎么处理的。

## 参考样例
